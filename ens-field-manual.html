Start here

ENS is not a domain registry. It is a hierarchy of delegated resolution authority.

Every feature in the protocol falls out of one rule: whoever controls a node controls resolution for everything beneath it, absolutely and recursively.

Subnames, Layer 2 names, gasless offchain names, imported DNS domains, custom registrars — none of these are special cases bolted on. They are all the same rule applied at a different depth. If you hold only one idea about ENS, hold this one; the rest of this page is elaboration.

The corollary catches people out: .eth is not the protocol. It is simply the most valuable instance of the general mechanism, and it is increasingly not the only one your app will encounter.

Architecture

Three jobs, three contracts, deliberately kept apart

DNS conflates ownership, sale, and lookup into one system. ENS splits them, and the split is what makes the protocol extensible: each layer can be replaced without touching the others.

The subtlety worth knowing

A registrar is not a protocol role. There is no registrar interface, no registration, no privileged status in the registry. A registrar is just a contract that happens to own a node and has opinions about who gets subnodes beneath it.

Hierarchy

Every node has an owner, including eth

The registry has no concept of a top-level domain. eth is an ordinary entry in the same mapping as nikola.eth — and like every entry, something owns it. That something is a contract.

Verify the middle link yourself:

Identity

On-chain, a name is a hash — the string is never stored

Before anything touches the chain, a name passes through a pipeline that ends in a 32-byte namehash. Every contract in ENS works exclusively with the output.

So where does the readable string survive?

In exactly two places: the calldata of the registration transaction, and one event log — ETHRegistrarController.NameRegistered(string name, …) emits the plaintext. The BaseRegistrar's identically-named event emits only the tokenId.

This is why the ENS Subgraph and tools like ens-indexer exist at all: reconstructing the hash-to-string map is a permanent, ongoing job that the protocol itself does not do.

Normalization is a security boundary, not cosmetics

ENSIP-15 defines what a valid name even is — Unicode handling, emoji sequences, confusable characters, script mixing. It needs thousands of codepoints of lookup data, so it cannot run on the EVM. It lives entirely in client libraries such as @adraffy/ens-normalize. Contracts see only hashes and are structurally incapable of validating a name. Skip normalization in your client and you have introduced a spoofing bug, not a display glitch.

Issuance

Four ways a name comes into existence

All four produce a name that resolves identically to a correct client. They differ entirely in who controls issuance and what it costs.

ENS is a mainnet-rooted resolution protocol whose data increasingly is not on mainnet. Lookup always starts on mainnet — that is the trust anchor — and then follows pointers outward.

Lifecycle

What happens to a .eth name over time

Unlike the rest of ENS, .eth names are rented, not owned outright. The registrar enforces a five-stage cycle; the registry knows nothing about any of it.

01

Registeredyour chosen duration

You hold the ERC-721, control the registry entry, and can edit records, create subnames, transfer, or renew. Renewal is permissionless — anyone may extend anyone's name without gaining control of it.

02

Expiredinstant

The registration end date passes. The name still points at its records, but it is frozen: no transfers, no marketplace listings, no resolver edits or subname creation on wrapped names.

03

Grace period90 days

Still resolving, still in your wallet, still recoverable at the ordinary renewal price — and nobody else can take it. This is your safety net, and it is generous. ENSv2 shortens it to 28 days.

04

Temporary premium21 days

The name must now be registered fresh rather than extended, and the previous owner has no priority. A premium is charged on top of the annual fee, starting at $100,000,000 and decaying to zero.

05

Availableindefinite

The premium reaches zero and the name returns to ordinary pricing, first come first served.

Why the premium starts at $100 million

It is not a valuation. It is an anti-sniping device: before it existed, bots claimed every expiring name the instant it dropped. A start price nobody will ever pay guarantees the auction begins above every bidder's limit and descends until it meets a real one.

Mechanics

Inside a registration transaction

Registration is commit-reveal across two transactions, so that a bot watching the mempool cannot front-run your name out from under you. Four contracts participate.

Two owners, and they can differ

The NFT owner (BaseRegistrar) holds the property right. The registry owner controls resolution. They are usually the same address, but the NFT owner can always call reclaim() to take registry control back. Selling the NFT transfers the underlying right regardless of who the registry currently lists — which is exactly the trap in any "I'll rent you control of my name" arrangement.

Note the last row. Forward resolution is hash-only; reverse records store the actual string. They have to — you cannot invert a hash to display a name. That asymmetry is the whole reason primary names work.

Resolution

Name to address, including the offchain path

Modern clients make one call to the Universal Resolver, which walks the registry, finds the resolver, and transparently handles the CCIP-Read branch.

Resolution

Address to name, and why it must be verified

Reverse resolution uses a reserved namespace: <lowercase-hex-address>.addr.reverse, read with name(bytes32). Anyone can set a reverse record to any string, so on its own it proves nothing.

What is changing

ENSv2, and the Namechain that isn't happening

ENS spent 2024 and 2025 building a dedicated Layer 2, Namechain, to host ENSv2. In February 2026 they cancelled it and moved ENSv2 directly onto mainnet, citing Ethereum's own scaling: registration gas costs fell roughly 99% over the preceding year as the gas limit went from 30M to 60M in 2025, with a 200M target for 2026. A great deal of writing still online assumes Namechain is coming. It is not.

What actually changes

  • Hierarchical registries replace the single flat registry. sub.alice.eth becomes a chain of entries linked by subregistry pointers, and any name owner can deploy their own subname registry with custom ownership and transfer rules. This is the headline change — the v1 combination of flat registry plus NameWrapper gives way to explicit, composable delegation. The pattern this page describes as a convention becomes first-class.
  • Per-account permissioned resolvers instead of one shared PublicResolver, with fine-grained per-record permissions. The resolver interface is unchanged, and custom resolvers remain fully supported.
  • Universal Resolver V2 as the single entry point that walks the new hierarchy and orchestrates CCIP-Read.
  • Grace period drops from 90 to 28 days, alongside one-step registration and stablecoin payments.

What you have to do about it

Less than you would expect. ENS's own guidance is that for most applications, readiness is simply updating your libraries — viem ≥ 2.35.0, ethers ≥ 6.17.0, ENSjs ≥ 4.2.3. What breaks is custom resolution logic and stale dependencies.

Status as of August 2026: contract documentation is published, the new App and Explorer are in public alpha, release is targeted during 2026, and production traffic is still largely v1. Verify the current deployment state before you build against it.

Practice

Integration checklist

01

Normalize every name before hashing it. Use @adraffy/ens-normalize or a library that embeds it. This is a security control, not a formatting step.

02

Compare namehashes, never raw strings. Any logic that matches names by string equality can be defeated by an unnormalized or trailing-dot variant.

03

Stop gating on .endsWith(".eth"). Treat any dot-separated string as a candidate name, or you will silently break every DNS-imported domain.

04

Keep a mainnet client even in an L2-only app. Resolution always begins on mainnet, whatever chain you are transacting on.

05

Specify coinType for multichain addresses. Otherwise you will route funds to the wrong network's address.

06

Forward-verify every reverse lookup before displaying a name, or fall back to the raw address.

07

Read live, not from an indexer, anywhere the answer is security-relevant. Indexed data lags, and offchain names emit no mainnet logs at all.

08

Use a real RPC provider. ENS resolution dies quietly when the mainnet endpoint does, and public RPCs fail exactly when a room full of people are demoing at once.
